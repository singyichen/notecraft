## 技術調研筆記：去識別化（De-identification）

去識別化要做的事很單純：把文件裡的個資換掉，讓資料能安全地交給下游處理，同時盡量保住原本的可讀性與分析價值。難的是「怎麼找出個資」與「換掉之後文件還能不能看」這兩件事，而它們的答案彼此牽制。

這一節記錄三件事：偵測個資有哪些路可走、一份文件從進到出中間發生了什麼、以及為什麼「有沒有真的刪掉」比「模型準不準」更關鍵。

### 選型光譜：三條路，不是二選一

偵測個資本質上是 NER（命名實體辨識）——從文字中找出人名、身分證號、地址、電話。課本把它談成「傳統 ML 對上深度學習」，但實務上還有第三條路，而且常常是真的被採用的那條：完全不用模型。

| 方案 | 怎麼運作 | 抓得好的 | 抓不到的 |
| --- | --- | --- | --- |
| 手刻規則 + 檢核碼 | regex 比對格式，再用檢核碼演算法驗證是否為合法號碼 | 身分證、統編、手機、市話、Email——格式明確且可驗算，誤判率近乎零 | 人名、地址、組織名這類沒有固定格式的實體 |
| 傳統 ML（CRF / HMM + 人工特徵） | 人工設計特徵（前後字、詞性、是否在姓氏表中），模型學特徵到標籤的映射 | 有一定規律但規則寫不完的欄位 | 需要語意理解的情境；特徵設計本身就是瓶頸 |
| 深度學習 NER（fine-tuned BERT） | 預訓練模型已具備語意表示，再以標註語料微調成逐字分類器 | 人名、地址、組織名等模糊實體，能靠上下文判斷 | 沒有檢核碼的概念，號碼類反而可能不如 regex 可靠 |

三者不是取代關係，而是各有守備範圍。實務上最常見的是**規則負責結構化欄位、模型負責模糊實體**，兩路獨立跑完後取聯集。

### 純規則能走多遠：一個真實案例

`dean9703111/data-deidentification` 是一個純前端的去識別化工具，`package.json` 裡只有四個相依套件（`pdf-lib`、`pdfjs-dist`、`jszip`、`@pdf-lib/fontkit`），**沒有任何機器學習套件**。它的技術調研文件明確否決了 NER，理由是需要大型模型下載、且仍需人工覆核。

那沒有模型要怎麼抓中文姓名？它的答案是四層規則防線：

| 層 | 做法 | 規模 |
| --- | --- | --- |
| 姓氏表 | 先確認第一個字是不是姓氏 | 122 個單姓、14 個複姓 |
| 雙分支 regex | 分別處理「姓 + 一字名」與「姓 + 二字名」 | 兩條規則 |
| 停用詞集合 | 把誤判的常見詞整批排除 | 216 個詞條 |
| 前文檢查 | 看命中位置前三個字決定是否採納，擋掉「甲方」「乙方」「任何」「如何」這類 | 約 43 個上下文詞 |

整個專案 3241 行 TypeScript、226 個測試案例。這是「不用深度學習能做到什麼程度」的實證：**結構化欄位幾乎全中，人名靠層層過濾勉強可用，地址與組織名基本放棄。**

下一節的資料流圖記錄了它與模型路線在管線上的差別——骨架相同，差別只在偵測那一段。

### 為什麼「純前端」不等於「在瀏覽器跑 NER」

原本我以為純前端工具之所以可行，是因為 transformers.js、ONNX Runtime Web 這些技術讓輕量 NER 模型能在瀏覽器跑推論。調研之後發現因果關係反過來了。

純前端的動機確實是信任與合規。處理個資若要上傳伺服器運算，等於違背去識別化的初衷，也直接踩到個資法的紅線。

但為了守住「資料完全不離開瀏覽器」這條線，這個專案付出的代價不是「用比較小的模型」，而是**完全不用模型**——因為模型檔案動輒數十 MB，首次載入的體驗與維護成本都不划算。

反過來看公司內部的繁中 NER 服務，選的是後端 Python 加上中研院 CKIP 的 fine-tuned BERT，純 CPU 推論。同一個問題，因為部署形態不同，選型結論完全相反。

所以真正的因果是：**部署形態決定了能不能用模型，而不是模型能力決定了部署形態。**

### 部署形態的第二個後果：授權義務

上面那個結論還有第二面。部署形態不只決定能不能用模型，也決定你背不背開源義務——而這件事必須在寫下第一行程式碼之前想清楚，因為它一旦混進已經上線的服務就很難拆。

去識別化會用到的兩個關鍵套件，授權剛好落在同一條分界線的兩側：

| 套件 | 用途 | 授權 | 網路條款 |
| --- | --- | --- | --- |
| `ckip-transformers` | 繁中 NER | GPL-3.0 | 無 |
| PyMuPDF | PDF 真遮蔽 | AGPL-3.0 | 有（第 13 條） |

GPL 的義務在「散布」時才觸發，而**把程式跑成內部網路服務並不算散布**。所以一個只用到 GPL 元件的內部服務，不產生任何開源義務。

AGPL 第 13 條正是為了補這個缺口而存在：只要使用者透過網路與程式互動，就必須向他們提供原始碼。

於是同一份程式碼，換個跑法就換一套義務：

| 部署形態 | 含 AGPL 元件 | 觸發第 13 條 |
| --- | --- | --- |
| 本機 CLI | 是 | 否 |
| 本機 Web UI（綁 127.0.0.1） | 是 | 否 |
| 內網服務 | 是 | 是 |

所以真正需要隔開的，不是「NER」與「PDF 處理」這兩個功能，而是「AGPL 元件」與「網路服務」這兩個屬性。想通這一層，架構的界線就會自己浮現——反過來也成立：只要沒有別人透過網路連進來，本機 Web UI 一樣安全。

這一節記的是技術面的判斷依據，實際採用前仍應經法務確認。

### 架構與資料流

不論用哪條偵測路線，去識別化管線的骨架是一樣的，關鍵在「壓平再分派」這個模式：把有結構的文件（PDF 的頁與文字區塊、Word 的 XML 節點）壓成一條連續字串，所有偵測與替換都在扁平的字元位置上運算，最後再把結果分派回原本的結構。

這個模式之所以必要，是因為個資很容易跨越結構邊界——PDF 為了調整字距，可能把「王小明」拆成兩個文字區塊；地址則常常跨行。若直接在結構節點上比對，這些都會漏抓。

### 讀原始碼才確認的一件事：offset 的語意

實作前有個疑慮：服務端允許的文字長度上限是 5000 字，而 BERT 的序列上限是 512 個 token。超出的部分會怎麼樣？如果是被截斷，那就是**個資靜默漏抓**——最危險的那種失敗，因為它不會報錯。

去讀 `ckip-transformers` 的原始碼後，答案是不會。長度超標時它另起一段，而不是丟棄：

```python
if len(input_ids_sent) + word_length > max_length:
    input_ids.append(input_ids_sent)
    input_ids_sent = []
```

更關鍵的是回傳的位置。它給的 `idx` 是 `index_char`——**原始輸入字串的字元位置**，不是內部切段後的相對位置。

這一點決定了整條管線能不能成立。模型回傳的位置可以直接餵進「壓平再分派」的對照表；若 offset 是相對於內部切段的，就得自己還原位移。而那正是最容易出錯、又最不容易被發現的一類 bug——**貼錯位置的假名，看起來跟貼對的一樣正常。**

殘留的風險小得多但仍存在：連續超過 510 個 token 都沒有出現分隔符的文字，會在任意位置被硬切，跨越切點的實體會解碼失敗。契約文件的表格與清單有機會踩到。

這件事留下的教訓是：**要依賴一個函式庫的 offset 語意，就去讀它的原始碼，不要讀 README。** 並且要為這個語意寫一條測試（斷言 `text[start:end]` 等於回傳的實體字串），這樣升級版本時語意若改變，會立刻炸出來，而不是讓下游默默貼錯。

### 把模型接成服務之後才浮現的成本

選擇用現成模型，省掉的是訓練與標註成本；但成本並沒有消失，而是搬到了「服務化」這一端。這四項都是讀完服務程式碼後才看見的：

| 成本 | 成因 | 徵狀 |
| --- | --- | --- |
| 超額訂閱 | Web 框架的執行緒池與 PyTorch 的核心層平行化相乘 | 並發數越高，每個請求反而越慢 |
| 冷啟動 | 模型是懶載入，第一個請求才觸發載入 | 服務已回報健康，但模型還沒就緒 |
| padding 浪費 | 批次推論會把所有片段補齊到最長那一筆的長度 | 批次內長度落差越大，浪費的計算越多 |
| 逐筆呼叫 | 介面一次只吃一個字串 | 處理 $N$ 頁就是 $N$ 次模型呼叫，放棄了批次的效益 |

第一項最違反直覺，所以值得單獨拆開看。兩層平行化各自都合理——框架用執行緒池讓同步端點不阻塞事件迴圈，PyTorch 用多執行緒吃滿 CPU——但它們相乘之後，執行緒數會遠超過核心數，變成互相搶佔。

判斷法則其實很單純：**CPU 密集的工作，並發度應該逼近核心數，而不是逼近請求數。**

### 真遮蔽與假遮蔽

比模型準確率更關鍵的一件事：**把文字蓋住不等於把文字刪掉。**

在 PDF 上畫一個黑色或白色矩形，視覺上個資消失了，但原始文字仍然存在於 PDF 的內容串流裡。用滑鼠選取複製、或用任何文字抽取工具打開，個資就會原樣跑出來。這是經典的「假遮蔽」事故，也是新聞上讀到的「政府公文塗黑後仍被還原」的成因。

要真的刪掉，必須從內容串流中移除對應的文字繪製指令，而不是在上面疊圖層。這也直接決定了驗收方式：

> 對每一份輸出檔重新抽取文字，斷言所有被偵測到的原始字串一個都找不到。

這條測試通過之前，模型準確率再高都沒有意義。

### 期末專案方向

綜合以上，期末專案不走「自己訓練一個 NER 模型」，而是走**評估與後處理改善**，並額外拉一條純規則的對照線：

| 項目 | 內容 |
| --- | --- |
| 受測對象 A | 現成的 CKIP fine-tuned BERT，原樣不動 |
| 受測對象 B | 純規則路線（姓氏表、雙分支 regex、停用詞、前文檢查），作為對照組 |
| 測試集 | 自行標註 200 至 300 句真實文件語句 |
| 指標 | 各類別的 entity-level precision、recall、F1 |
| 產出 | 兩條路線的逐類別對照表、漏抓型態分析、後處理規則層與其改善幅度 |

選這條路的理由是：真正的瓶頸不是模型架構而是**標註資料**。微調需要數千句標註（估計 30 至 60 小時的純標註工），而資料是真實個資、不能外包標註；評估只需要兩三百句，一兩天可完成，卻能產出目前沒有人量測過的資訊——CKIP 是在新聞語料上訓練的，它在契約文件上表現如何，並沒有現成答案。

要加上對照組 B，則是因為單獨一個 F1 數字讀不出意義，得有比較對象才知道那個數字算好還是壞。而且這一步正好把前面那張選型光譜表從紙上調研變成實測——「純規則抓得到什麼、抓不到什麼」目前只是引述來的結論，跑過同一份測試集之後就會變成自己的數據。

預期的弱點在地址與組織名，這也正好是純規則路線同樣放棄的那一塊。兩條路線在同一處失守，這件事本身就是結果的一部分。

關於量測順序有一點要分清楚：服務端的超額訂閱只影響延遲，不影響準確率——執行緒互相搶佔不會改變模型的輸出。所以準確率那條線現在就能開始量，不必等服務調校；只有延遲基線必須先把執行緒環境弄乾淨再量，否則量到的是搶佔而不是模型本身的能力。

### 需要補的先備知識

這條路線真正執行的深度學習動作只有一個：推論。但要能解釋「為什麼會漏抓」，需要懂的東西遠多於「跑一次推論」，而且集中在課程沒有涵蓋的那一塊。

| 技術 | 會不會實際動手寫 | 需不需要懂 | 理由 |
| --- | --- | --- | --- |
| 推論（forward pass） | 只是呼叫 API | 淺 | 一個 POST 就結束了 |
| 序列標註與 BIO 標籤體系 | 會，標註測試集時 | 深 | 這是 NER 的問題形式化，決定 ground truth 長什麼樣 |
| 中文 char-level tokenization | 不會 | 深 | offset 語意與 510 token 硬切風險都源自這裡 |
| 預訓練加微調的範式 | 不會 | 深 | 新聞語料訓練、契約文件推論的落差就是整個專案的論點 |
| Transformer 自注意力 | 不會 | 中 | 只需要到「為什麼上下文能判斷人名」，不必推導 QKV |
| 訓練迴圈與反向傳播 | 不會 | 已具備 | 第 10、11 週手刻過一次 |
| RNN、LSTM 加 CRF | 不會 | 選配 | ch15 可整章跳過，除非要再多加一條對照線 |
| CNN、GAN、GNN、強化學習 | 不會 | 不需要 | ch14、17、18、19 與本專案無關 |

課程教到的極限是第 10、11 週：手刻過前向與反向傳播、知道 tensor 與 autograd 怎麼記帳。序列標註、預訓練加微調的範式、Transformer 都沒教，要自學 ch16 的 BERT 與 token classification 那半章。

要補的東西按「會不會擋住進度」排成四層：

| 層級 | 內容 | 課程有沒有教 | 何時能開始 |
| --- | --- | --- | --- |
| Tier 0 | 標註規範設計 | 無關 | 現在，不必等任何進度 |
| Tier 1 | 序列標註的評估方法論 | 只教了分類版本 | 與標註同時進行 |
| Tier 2 | 模型內部與訓練分佈落差 | 沒教 | 分析結果之前 |
| Tier 3 | 量測環境的工程議題 | 沒教 | 只有延遲那條線需要 |

Tier 0 是整個專案最被低估、也最可能毀掉數字的一環。「臺北市信義區松智路 1 號 5 樓之 3」算一個地址實體還是拆成多個？「王小明先生」的敬稱在不在邊界內？「甲方（○○股份有限公司）」的括號算不算組織名的一部分？這些沒有標準答案，但規範必須盡量對齊 CKIP 訓練時採用的規範，否則量到的「錯誤」有一部分只是規範不合，不是模型能力問題。這也是評估類專案最容易被質疑的地方。

Tier 1 是專案的主體，而它跟第 7 週學的分類評估並不是同一套：

| 概念 | 課程涵蓋 | 為什麼這裡不一樣 |
| --- | --- | --- |
| entity-level 對 token-level 計分 | 沒教 | 抓到「王小」漏掉「明」，token-level 得 0.67 分，entity-level 是 0 分。去識別化只有後者有意義，漏一個字就是外洩 |
| 嚴格匹配對部分匹配 | 沒教 | seqeval 的預設模式與 strict 模式結果不同，報告要講清楚報的是哪一種 |
| micro 對 macro 平均 | 部分 | 組織名樣本少、人名樣本多，micro 會被人名淹沒，看不出預期中的弱點 |
| 樣本數與信賴區間 | 沒教 | 200 至 300 句這個規模的最大風險 |

最後一項是目前規劃裡最脆弱的地方。若組織名在整份測試集只出現二十來次，那個 F1 的誤差範圍會寬到結論站不住。因應方式是標註前先抽三十句數一數各類別的出現頻率，往回推兩三百句能得到多少實體；撐不到一定數量的類別，要麼加大樣本，要麼在報告裡誠實標成樣本不足。

Tier 2 不需要會寫 BERT，只需要能回答「為什麼會漏」。三個成因分別是訓練語料的分佈落差（新聞裡的地址是「台北市」，契約裡是完整門牌與樓層，後者在訓練分佈中幾乎不存在）、模型沒有檢核碼的概念（`A123456789` 與 `A123456788` 在它眼裡沒有差別，這解釋了號碼類為什麼 regex 反而贏）、以及超長無分隔符文字被硬切造成的標籤斷裂。

## 期末專案定案：預測標註者分歧，協助安排複核

### 題目與方案決策

期末專案正式採用**方案 B：真實多標註者資料 + 多語文字 Embedding + 傳統分類模型，GNN 作為選做比較**。

暫定題目：

> **以文字特徵與標註歷史預測標註分歧：英文與繁體中文複核排序之比較研究**

Label Suite 尚未正式累積真實使用紀錄，因此期末階段先以公開的真實多標註者資料驗證方法，再建立一份小型繁體中文 pilot。這兩條證據的角色不同：英文公開資料回答「方法在真實多標註資料上是否可行」，繁中 pilot 回答「方法能否轉移到論文的主要使用者情境」。

| 層級 | 必要性 | 內容 |
| --- | --- | --- |
| 真實英文資料 | 必做 | 從 TID-8 選一個保留 `item_id`、`annotator_id` 與個別標籤的子資料集 |
| 繁體中文 pilot | 必做 | 從論文目標情境抽取 150 至 300 筆文字，每筆由至少 3 位標註者獨立標註 |
| 隨機與規則基準 | 必做 | 隨機排序、可見標籤熵、票數差距與簡單統計 |
| 傳統分類模型 | 必做 | Logistic Regression 與 Gradient Boosting |
| 多語 Embedding | 必做 | 以同一模型處理英文與繁中；本機模型優先，外部 API 作選配對照 |
| GraphSAGE | 選做 | 驗證 item–annotator 圖結構是否有穩定額外效益 |
| 完整 Label Suite 功能 | 不做 | 本專題只做離線原型與資料需求建議，不開發正式複核佇列 |

專題目標是**排序較可能出現分歧的資料項目**，不是取代標註者、裁定哪一個標籤正確，也不把分歧直接等同於標註錯誤。

### 英文與繁體中文能否一起處理

可以，但要把「模型支援中文」與「研究已證明繁中有效」分開。

多語 Embedding 可以把英文與中文映射成同維度向量，下游的 Logistic Regression、Gradient Boosting 或 GNN 都只接收數值特徵，因此技術管線可以共用。然而模型宣稱支援 `zh`，不代表它一定掌握臺灣繁體中文的用詞、標點、語氣與領域術語；仍需要繁中資料獨立驗證。

建議的 Embedding 選型如下：

| 模型 | 定位 | 專題角色 | 注意事項 |
| --- | --- | --- | --- |
| [`BAAI/bge-m3`](https://huggingface.co/BAAI/bge-m3) | 開源多語 Embedding，1024 維、MIT License | **推薦作主模型**，可本機一次處理英文與中文 | 官方資料以 `zh` 為單位，仍要用臺灣繁中 pilot 驗證 |
| [`voyage-4-lite`](https://docs.voyageai.com/docs/embeddings) | 多語 Embedding API，偏成本與延遲效率 | 有額度時作 API 對照 | 公開資料可送 API；論文真實資料需先確認資料治理 |
| [`mistral-embed`](https://docs.mistral.ai/studio/knowledge-rag/embeddings) | 通用文字 Embedding API | Voyage 的替代方案，不需要兩者都做 | 不使用 Mistral 對話模型產生判斷 |

`BGE-M3` 的論文與模型卡描述其多語能力涵蓋超過 100 種語言，且可本機產生 dense embedding。這適合論文以繁體中文為主的情境：英文與繁中可以共用同一特徵產生器，也不必把尚未確認可外傳的文字送到第三方 API。[BGE-M3 論文](https://arxiv.org/abs/2402.03216)

雙語實驗要分成三種，不混成一個模糊的「多語結果」：

1. **英文單語模型**：在英文 TID-8 訓練與測試，驗證方法可行性。
2. **繁中單語模型**：在繁中 pilot 交叉驗證，回答論文主要使用情境。
3. **跨語轉移實驗**：英文訓練、繁中測試，或英文與繁中合併訓練；只當探索性結果，不取代繁中單語驗證。

若以同一指標 $M$ 衡量兩種語言，可以另外報告語言落差：

$$
\Delta_{\text{lang}} = M_{\text{zh-TW}} - M_{\text{en}}
$$

必須同時列出 $M_{\text{zh-TW}}$ 與 $M_{\text{en}}$，不能只報 pooled score，否則英文樣本量較大時會遮住繁中的弱點。

翻譯英文資料不能直接取代繁中人類標註。翻譯可能消除或新增歧義，而英文標註者的分歧也不是繁中使用者的分歧。機器翻譯資料最多只能當 Embedding 的跨語壓力測試，不得當作繁中主證據。

### 正式研究問題與假設

主要研究問題：

> 在一筆資料只取得部分標註時，能否預測完整標註結果是否會出現分歧，並在固定複核預算下，比隨機或簡單分歧分數更早找出需要人工關注的項目？

子問題：

1. 只使用目前可見標籤的 entropy 與票數差距，可以做到多好？
2. 加入文字 Embedding 後，是否能找出「目前暫時一致，但後續可能出現分歧」的項目？
3. 英文與繁中是否呈現相似改善，或存在明顯語言落差？
4. 加入 annotator 歷史與圖結構後，GraphSAGE 是否穩定勝過非圖模型？
5. 模型增益是否足以抵銷資料需求、維護成本與可解釋性損失？

預先設定的假設：

| 假設 | 內容 |
| --- | --- |
| H1 | 可見標籤 entropy 會顯著勝過隨機排序 |
| H2 | 多語 Embedding 加上結構化特徵，會勝過只使用可見標籤統計的基準 |
| H3 | 在具備足夠重複 annotator 與連通圖結構時，GraphSAGE 可能進一步改善排序 |
| H4 | 英文模型的改善不能直接代表繁中；繁中結果需獨立成立 |

### 問題形式化

令第 $i$ 個資料項目為 $x_i$，標籤集合為 $\mathcal{C}$，完整標註集合為 $A_i$。類別 $c$ 在完整標註中的比例為：

$$
p_{ic}
=
\frac{\sum_{a \in A_i}\mathbf{1}(y_{ia}=c)}{|A_i|}
$$

其中 $y_{ia}$ 表示 annotator $a$ 對項目 $i$ 的標籤。使用正規化 entropy 表示完整分歧程度：

$$
H_i
=
\frac{-\sum_{c \in \mathcal{C}}p_{ic}\log p_{ic}}
{\log |\mathcal{C}|}
$$

$H_i=0$ 代表所有標註完全一致；越接近 $1$，代表標籤分布越分散。

主要二元目標先定義為是否出現任何分歧：

$$
z_i
=
\mathbf{1}
\left(
\left|\{y_{ia}:a\in A_i\}\right| > 1
\right)
$$

若探索後發現「任何分歧」的陽性比例過高或過低，才改用預先固定的高分歧門檻：

$$
z_i^{(\tau)} = \mathbf{1}(H_i \ge \tau)
$$

門檻 $\tau$ 只能由訓練集決定，固定後才可評估測試集。

部分觀測實驗中，只向模型揭露 $r$ 份標註，記為 $O_i$；其餘標註 $U_i=A_i\setminus O_i$ 全部隱藏。主要設定為 $r=2$。模型輸出風險分數：

$$
s_i
=
f_{\theta}
\left(
x_i,
O_i,
\text{history}(a),
G_{\text{visible}}
\right)
$$

其中 $G_{\text{visible}}$ 只能包含預測當下已可見的 annotation edges。測試項目的隱藏標註不得出現在特徵、統計或圖 adjacency 中。

## 階段 1：固定研究問題與成功標準

### 階段目標

在碰模型之前，先把「何時預測、預測什麼、模型能看見什麼」寫成實驗協議。這一階段若沒有固定，後面很容易把完整標註的資訊不小心放進特徵，得到看似漂亮但無法上線的結果。

### 要做的事情

1. 固定主要情境：每筆資料已取得前兩份標註，系統要判斷是否值得安排額外複核。
2. 固定主要 target：完整標註是否出現分歧。
3. 固定主要排序指標：`Recall@10%`。
4. 固定次要指標：`Precision@5%`、`Precision@10%`、`Recall@5%`、`Recall@20%`、PR-AUC 與 `Lift@10%`。
5. 固定英文與繁中分開報告，不只報 pooled score。
6. 列出不研究的問題：不做真值聚合、不評分標註者好壞、不自動決定最終標籤。

### 技術調研

| 主題 | 要查證的問題 | 調研產出 |
| --- | --- | --- |
| Annotation disagreement | 分歧何時是主觀差異、何時是標註錯誤或規範不清？ | 名詞定義與研究邊界 |
| Review prioritization | 文獻是預測錯誤、估計不確定性，還是排序複核項目？ | 問題類型比較表 |

- 能以一句話說明模型可見資訊與隱藏資訊。

## 階段 2：公開資料、繁中資料與授權調研

### 階段目標

找到真正保留「誰標了哪一筆、給了什麼標籤」的資料。只有聚合後 majority label 的資料不能支援 annotator–item 圖，也不能研究分歧形成過程。

### 英文主資料：TID-8

[`MichiganNLP/TID-8`](https://huggingface.co/datasets/MichiganNLP/TID-8) 是目前的第一候選。它整合八個具有真實分歧的英文語言理解資料集，涵蓋 NLI、情緒、仇恨言論與幽默等任務，並保留 annotator 與個別 annotation 的關係。[原始研究](https://aclanthology.org/2023.findings-emnlp.832/)

先調研三個候選子資料集：

| 子資料集 | 優點 | 風險 | 初步優先度 |
| --- | --- | --- | --- |
| Sentiment | 問題直觀、適合先做分類與分歧排序 | 分歧高度主觀，需確認 label schema | 高 |
| MultiDomain Agreement | 與 disagreement 主題直接相關 | domain 差異可能形成混雜因素 | 中 |
| GoEmotions | 標註量大、annotator 重複度可能較好 | 多標籤且類別多，超出期末專案範圍 | 低 |

TID-8 的總 Dataset Card 授權欄目前未完整標示，且每個子資料集有自己的授權與引用。不能因為 Hugging Face 可以下載就假設可以任意使用；必須追到原始來源逐一記錄。

### 繁體中文資料策略

目前不把簡體中文資料或機器翻譯資料直接當成繁中主證據。優先順序是：

1. 搜尋保留穩定 annotator ID 的繁體中文多標註分類資料。
2. 若沒有合適公開資料，建立 150 至 300 筆繁中 pilot。
3. 每筆至少 3 位標註者，形成約 $450$ 至 $900$ 份 annotation。
4. Pilot 題目必須貼近論文主要使用情境，不能只為了方便而選與產品無關的情緒分類。
5. [`YACLC`](https://github.com/blcuicall/YACLC) 等中文多標註資料可作方法備援調研，但它是中文學習者語料且任務不同，不能取代臺灣繁中 pilot。

### 資料探索要計算的內容

對每個候選資料集建立以下統計：

- 唯一 item 數、annotator 數、annotation 數。
- 每個 item 的 annotation 數分布。
- 每位 annotator 的 item 數分布。
- 類別分布與缺失標籤。
- 完全一致、部分分歧與高 entropy item 的比例。
- Item–annotator 矩陣稀疏度。
- 二分圖的連通分量數與最大連通分量涵蓋率。
- 只標一次的 annotator 比例。
- 重複 item、重複 annotation 與格式異常。

令 item 數為 $N_I$、annotator 數為 $N_A$、實際 annotation edge 數為 $|E|$，圖稀疏度可記為：

$$
\operatorname{Sparsity}
=
1-
\frac{|E|}{N_I N_A}
$$

### 資料合格門檻

- 至少 1,000 個英文可用 item。
- 每個 item 至少 3 份 annotation。
- 至少 10% item 有分歧。
- 大部分 annotator 不只標一筆。
- 具備穩定 item ID、annotator ID 與 label。
- 授權允許課程研究、論文引用與必要的衍生統計。

### 決策分支

若 TID-8 第一個子資料集不合格，先換另一個真實子資料集；只有找不到合理真實資料時，才使用模擬 annotator 作備援。模擬資料只能證明程式管線與方法行為，不能代表真實人類。

- 候選資料比較表。
- 主資料 Dataset Card。
- 授權與引用清單。
- 圖結構 EDA。
- 標準化資料 schema：`item_id`、`text`、`annotator_id`、`label`、`language`、`source_dataset`。

## 階段 3：建立雙語、部分觀測與無洩漏資料協議

### 階段目標

建立能模擬「已取得少量標註，要不要把這筆送去複核」的資料切分。這一階段的品質比選哪個模型更重要。

### Item-level split

以 `item_id` 分組切分：

$$
\mathcal{D}
=
\mathcal{D}_{\text{train}}
\cup
\mathcal{D}_{\text{val}}
\cup
\mathcal{D}_{\text{test}}
$$

$$
|\mathcal{D}_{\text{train}}|:
|\mathcal{D}_{\text{val}}|:
|\mathcal{D}_{\text{test}}|
=
70:15:15
$$

同一個 item 的所有 annotation 必須留在同一 split。不能逐 annotation 隨機切分，否則模型可能在訓練時已看過測試 item 的其他標註。

TID-8 已提供 annotation split 與 annotator split，但本專題的預測單位是 item，仍需重新驗證它的 split 是否符合 item isolation；不符合就自行建立 group split。

### 部分標註 reveal protocol

對每個 item：

1. 從完整標註中抽出 $r=2$ 份成為可見集合 $O_i$。
2. 其餘標註成為隱藏集合 $U_i$。
3. 只用 $O_i$ 與 training history 建立特徵。
4. 用完整 $A_i$ 計算 target $z_i$。
5. 因公開資料通常沒有可靠時間順序，重複多個 random reveal seeds。

報告中稱為「隨機部分觀測模擬」，不能寫成真實時間序列預測。

### 繁中 pilot 設計

- 樣本：150 至 300 筆繁中資料。
- 標註者：至少 3 位，最好 5 位。
- 每位標註者先閱讀同一份規範，再獨立作答。
- Pilot 前用 20 至 30 筆做校準，但校準討論後的資料不要直接混入正式測試。
- 同時保存原始 label、時間、規範版本與後續裁決，不只保存 majority label。
- 先計算 raw agreement、Fleiss' kappa 或 Krippendorff's alpha，了解任務是否真的存在可研究的分歧。

### 冷啟動測試

建立兩種測試情境：

1. **已知 annotator**：測試 annotator 曾在 training items 出現。
2. **未知 annotator**：測試 annotator 完全不在 training graph。

如果模型只在已知 annotator 有效，論文結論必須限定為「對既有標註團隊有效」，不能宣稱能直接泛化到新標註者。

### 洩漏檢查

禁止使用：

- Test item 的隱藏標註。
- Test item 的完整 entropy 或 majority label 作特徵。
- 用 validation 或 test annotation 算出的 annotator 歷史表現。
- 完整圖預訓練後再切 train/test。
- 將 target edge 放入 GNN message passing。
- 用完整資料調整 $\tau$ 或決定特徵。

### 階段產出

- 固定的 split manifest。
- Reveal seed manifest。
- 繁中標註規範與資料字典。
- 自動洩漏檢查測試。
- 英文與繁中各自的資料流程圖與樣本統計。

## 階段 4：建立最低基準線

### 階段目標

回答「完全不使用 Embedding 或 GNN 時，可以做到多好」。所有後續模型都必須在相同 split、相同可見資訊與相同 $K$ 下比較。

### Baseline 0：隨機排序

- 對測試 item 隨機排序。
- 至少執行 30 個 random seeds。
- 回報平均、標準差與 95% confidence interval。

### Baseline 1：可見標註規則

從 $O_i$ 計算：

- 可見標籤是否已分歧。
- 可見標籤 entropy。
- 最高票與第二名票數差距。
- 可見標籤種類數。
- 可見標註數。

這條基準非常重要：如果它已經足夠好，就沒有理由先上 GNN。

### Baseline 2：文字表面與 metadata

不使用預訓練 Embedding，只使用：

- 字元數與 token 數。
- 問號、否定詞、模糊詞與程度詞數量。
- 文本是否包含多句、引號或條件句。
- 類別、domain 與來源資料集。
- 可見標註統計。

模型使用 Logistic Regression、Decision Tree 與 Gradient Boosting；Decision Tree 主要用於解釋，最終比較以 Logistic Regression 和 Gradient Boosting 為主。

### Baseline 3：加入 annotator 歷史

只從 training items 計算：

- 歷史標註數。
- 各類別標註比例。
- 與同組其他 annotator 的歷史分歧率。
- 與 training majority label 的一致率。
- 覆蓋的 domain 數。
- 歷史資料不足指示值。

Validation 與 test annotator 的統計要用 training-only 或 out-of-fold 方式產生，避免 target leakage。

### 排序指標

設測試集排序後前 $K$ 筆為 $\operatorname{TopK}$，真正分歧集合為 $\mathcal{P}$：

$$
\operatorname{Precision@K}
=
\frac{|\operatorname{TopK}\cap\mathcal{P}|}{K}
$$

$$
\operatorname{Recall@K}
=
\frac{|\operatorname{TopK}\cap\mathcal{P}|}{|\mathcal{P}|}
$$

若測試集共有 $N$ 筆，分歧盛行率為：

$$
\pi
=
\frac{|\mathcal{P}|}{N}
$$

則相對於隨機抽查的提升為：

$$
\operatorname{Lift@K}
=
\frac{\operatorname{Precision@K}}{\pi}
$$

固定預算比例 $b$ 時：

$$
K=\lfloor bN\rfloor,
\qquad
b\in\{0.05,0.10,0.20\}
$$

主要指標固定為 `Recall@10%`，因為它直接回答「只能複核 10% 資料時，可以涵蓋多少真正分歧」。

### 階段產出

| 模型 | PR-AUC | P@5% | R@5% | P@10% | R@10% | Lift@10% |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Random | | | | | | |
| Visible entropy | | | | | | |
| Logistic Regression | | | | | | |
| Gradient Boosting | | | | | | |

完成條件是至少一個可訓練模型完整跑通，並確認重跑可以得到相同 split 與評估結果。

## 階段 5：多語 Embedding 與雙語模型比較

### 階段目標

驗證文字語意是否能在可見標註統計之外，辨識出較容易引發分歧的內容。

### 主模型與選配模型

主線使用 `BAAI/bge-m3` 產生英文與繁中 dense embedding。它是開源、多語且可本機執行，能避免公開英文資料與未來論文私有資料走不同技術管線。

若時間與 API 額度允許，再從 Voyage `voyage-4-lite` 或 Mistral `mistral-embed` 選一個作外部對照。兩個 API 不必同時比較，否則研究焦點會從複核排序偏成供應商評比。

Embedding 本身不會直接輸出分歧機率。完整模型是：

$$
\mathbf{e}_i
=
\operatorname{Embed}(x_i)
$$

$$
\hat{p}_i
=
\sigma
\left(
\mathbf{w}^{\mathsf{T}}
[\mathbf{e}_i;\mathbf{v}_i]
+b
\right)
$$

其中 $\mathbf{v}_i$ 是可見標註與 annotator 歷史的結構化特徵，$[\cdot;\cdot]$ 表示向量串接。

### 必做消融

| 實驗 | 文字 Embedding | 可見標註統計 | Annotator 歷史 | 語言欄位 |
| --- | ---: | ---: | ---: | ---: |
| E1 | ✓ | | | |
| E2 | | ✓ | ✓ | |
| E3 | ✓ | ✓ | ✓ | |
| E4 pooled bilingual | ✓ | ✓ | ✓ | ✓ |

模型至少比較：

- Logistic Regression。
- Gradient Boosting 或 XGBoost。
- 英文單語模型。
- 繁中單語模型。
- 英繁 pooled model。
- 英文訓練、繁中 zero-shot 測試，僅作探索結果。

### Embedding 工程調研

- 是否需要固定 pooling 與 normalization 方法。
- 1024 維向量是否直接輸入 Logistic Regression，或需要 PCA。
- 不同語言的向量 norm 與分布是否偏移。
- 繁中標點、全形字元與臺灣領域詞是否需要正規化。
- 長文本截斷位置是否會丟失造成分歧的上下文。
- Batch size、CPU／GPU 記憶體與推論時間。
- 模型版本固定、cache invalidation 與可重現性。

每筆快取至少保存：

```text
item_id
language
provider
model_name
model_revision
dimension
text_hash
created_at
embedding
```

### 外部 API 資料治理

公開資料可依授權與供應商條款評估後送 API；未來 Label Suite 或論文真實資料在送出前，必須確認：

- 是否含個資或機密內容。
- API 供應商是否保留輸入。
- 資料所在地與存取權限。
- 是否允許論文研究使用。
- 是否需要去識別化。

### 階段產出

- 固定版本的雙語 embedding cache。
- 英文、繁中與 pooled 結果表。
- E1–E4 消融分析。
- API 成本、延遲與資料治理比較表。
- 語言落差 $\Delta_{\text{lang}}$。

## 階段 6：GraphSAGE 異質二分圖實驗（選做）

### 階段目標

在相同可見資訊下，驗證圖結構能否穩定勝過 Embedding 加傳統分類器。GNN 是待驗證方法，不是預設答案。

### 圖結構

建立兩種 node：

- `item`：特徵為文字 Embedding、長度、語言與 domain。
- `annotator`：特徵為 training-only 歷史標籤分布、分歧率、標註量與冷啟動指示。

建立 relation-specific edge：

```text
annotator --annotated_as_<label>--> item
item --rev_annotated_as_<label>--> annotator
```

使用不同 edge type 表示 label，可以避免最小版 GraphSAGE 完全忽略 edge label。PyTorch Geometric 的 [`HeteroData`](https://pytorch-geometric.readthedocs.io/en/latest/notes/heterogeneous.html) 可分別保存不同 node 與 edge type，也支援將 GraphSAGE 轉成異質圖模型。

### 最小模型

- 兩層 GraphSAGE。
- Hidden dimension 先測 64 與 128。
- Dropout 先測 0.2 與 0.5。
- Item node 輸出 disagreement probability。
- 使用 validation PR-AUC early stopping。
- 至少 5 個 model seeds。

GraphSAGE 的一層聚合可寫成：

$$
\mathbf{h}_i^{(\ell+1)}
=
\sigma
\left(
\mathbf{W}_1\mathbf{h}_i^{(\ell)}
+
\mathbf{W}_2
\operatorname{mean}_{j\in\mathcal{N}(i)}
\mathbf{h}_j^{(\ell)}
\right)
$$

處理類別不平衡時，可使用帶正類權重的 binary cross-entropy：

$$
\mathcal{L}
=
-\frac{1}{N}
\sum_{i=1}^{N}
\left[
w_{+}z_i\log \hat{p}_i
+
(1-z_i)\log(1-\hat{p}_i)
\right]
$$

### 公平比較要求

| 模型 | 文字 | 可見標註 | Annotator 歷史 | 圖結構 |
| --- | ---: | ---: | ---: | ---: |
| Logistic Regression | ✓ | ✓ | ✓ | |
| Gradient Boosting | ✓ | ✓ | ✓ | |
| GraphSAGE | ✓ | ✓ | ✓ | ✓ |

三個模型必須使用同一批 item、同一 reveal seed 與相同可見資訊。

### GNN 特有洩漏風險

- Test item 的 hidden edges 不得進圖。
- Target edge 不得參與 message passing。
- 不得先用完整圖學 embedding 再切 split。
- Test item 若沒有可見 edge，模型只能依賴 item features。
- 未知 annotator 不可只靠 training 中學到的 ID embedding。

### 停損條件

若 GNN 符合以下條件，才值得在結論中列為候選：

- `Recall@10%` 平均提升至少 3 個百分點。
- 5 個 seeds 中至少 4 個勝過最佳非圖模型。
- Paired bootstrap 的改善不是明顯不穩定。
- 推論與維護成本仍符合未來 Label Suite 情境。

若不符合，正式結論就是「圖結構沒有提供足以抵銷複雜度的穩定增益，應先採簡單模型」。這仍然是完整且有產品價值的研究結果。

## 階段 7：穩健性、雙語誤差與失敗案例分析

### 階段目標

確認結論不依賴單一 random seed、單一 reveal 結果、單一語言或單一複核預算。

### 穩健性矩陣

| 維度 | 測試值 |
| --- | --- |
| Reveal 數量 | $r\in\{1,2,3\}$ |
| 複核預算 | $b\in\{0.05,0.10,0.20\}$ |
| 模型 seed | 至少 5 個 |
| Reveal seed | 建議 10 個 |
| 語言 | 英文、繁中、pooled |
| Annotator | 已知、未知 |
| 特徵 | text only、metadata only、combined、graph |

### 統計方法

- 以 item 為單位做 paired bootstrap。
- 回報平均、標準差與 95% confidence interval。
- 不只呈現最佳 seed。
- 所有模型在同一 bootstrap sample 上比較。
- 樣本數太小時，不把很小的數值差異解讀成模型優勢。

### 雙語錯誤分析

英文與繁中各抽查：

- 30 個 false positives。
- 30 個 false negatives。
- 20 個高信心正確案例。

錯誤類型至少區分：

- 文字本身有多種合理解讀。
- 缺少前後文或外部知識。
- 否定、反諷與條件句。
- Label schema 邊界不清。
- 少數 annotator 的系統性偏好。
- 臺灣用語、繁簡差異或領域術語。
- Embedding 截斷或正規化問題。
- 模型只記住特定詞彙或 domain。

### 公平與倫理

- 不把 disagreement 直接稱為 error。
- 不將低一致率 annotator 自動標成低品質人員。
- 不以人口屬性作自動懲罰或排班依據。
- Annotator ID 必須假名化。
- 模型只排序 item，不自動裁決標籤。
- 需要人工檢查模型是否對特定語言、類別或 annotator 群體產生系統性偏差。

### 階段產出

- 穩健性矩陣。
- Paired bootstrap 信賴區間。
- 英文與繁中錯誤分類表。
- 代表性成功與失敗案例。
- 模型限制與適用條件。

## 階段 8：結果判讀、論文寫作與 Label Suite 銜接

### 階段目標

把模型比較轉成可以執行的產品與研究決策，而不是只留下最高分模型。

### 決策規則

| 實驗結果 | 結論與建議 |
| --- | --- |
| 可見 entropy 已經最好 | 先採透明規則排序，不導入模型 |
| Embedding 穩定提升 | 採 Embedding + 簡單分類器作候選 |
| GNN 顯著且穩定提升 | 等真實繁中平台資料累積後，再評估 GNN 導入 |
| 英文有效、繁中無效 | 不可直接導入論文目標情境；需補繁中資料或領域調整 |
| 模擬有效、真實資料無效 | 不宣稱可改善正式複核流程 |
| 所有方法都不穩定 | 暫不做自動排序，優先改善資料紀錄與標註規範 |

### Label Suite 未來資料需求

至少要能串起：

```text
project_id
item_id
task_schema_version
annotator_pseudonymous_id
assignment_id
annotation_id
label_payload
annotation_started_at
annotation_submitted_at
review_id
review_outcome
adjudicated_label
adjudication_reason
reviewer_pseudonymous_id
model_score
model_version
visible_annotation_count
```

必須保留評分當下已可見的標註版本，否則未來無法重建模型當時真正知道的資訊。也要區分複核原因是分歧、標註錯誤、規範問題、資料缺漏或其他原因；否則只能預測「分歧」，無法驗證是否真的節省複核成本。

### 論文章節

1. 問題背景與繁中使用情境。
2. Annotation disagreement 與複核排序相關研究。
3. 英文公開資料與繁中 pilot。
4. 部分觀測與 item-level split。
5. 隨機、規則與傳統 ML baselines。
6. 多語 Embedding 模型。
7. GraphSAGE 選做模型。
8. Precision@K、Recall@K 與 PR-AUC 結果。
9. 雙語、冷啟動、消融與穩健性分析。
10. 錯誤分析、倫理與限制。
11. 對 Label Suite 的資料與流程建議。

### 最終交付物

- 可重現的資料處理與實驗程式。
- 固定 split 與 reveal manifests。
- 英文與繁中 Dataset Cards。
- 標註規範與資料字典。
- Baseline、Embedding 與選做 GNN 比較表。
- 雙語錯誤案例與信賴區間。
- 一頁產品決策摘要。
- 期末報告與簡報。

## 專題程式碼與 Repo 邊界

目前不必先拆成新 repo。期末專題仍定位成 Label Suite 的技術調研與離線原型，先把資料處理、設定、模型與結果放在獨立實驗目錄，避免未驗證模型直接成為正式功能。

符合以下任一條件時再拆 repo：

- 課程要求獨立交件。
- 需要獨立部署 demo。
- Python／PyTorch 依賴與 Label Suite 主程式明顯不同。
- 實驗已有自己的版本、資料下載與重現流程。

正式公開前另確認 Label Suite 程式碼授權、公開資料授權、繁中 pilot 的同意與去識別化方式，以及論文是否允許公開原始文字與個別 annotation。
