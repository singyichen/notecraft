## 技術調研筆記：去識別化（De-identification）

去識別化要做的事很單純：把文件裡的個資換掉，讓資料能安全地交給下游處理，同時盡量保住原本的可讀性與分析價值。難的是「怎麼找出個資」與「換掉之後文件還能不能看」這兩件事，而它們的答案彼此牽制。

這一節記錄三件事：偵測個資有哪些路可走、一份文件從進到出中間發生了什麼、以及為什麼「有沒有真的刪掉」比「模型準不準」更關鍵。

### 選型光譜：三條路，不是二選一

偵測個資本質上是 NER（命名實體辨識）——從文字中找出人名、身分證號、地址、電話。課本把它談成「傳統 ML 對上深度學習」，但實務上還有第三條路，而且常常是真的被採用的那條：完全不用模型。

| 方案 | 怎麼運作 | 抓得好的 | 抓不到的 |
| --- | --- | --- | --- |
| 手刻規則 + 檢核碼 | regex 比對格式，再用檢核碼演算法驗證是否為合法號碼 | 身分證、統編、手機、市話、Email——格式明確且可驗算，誤判率近乎零 | 人名、地址、組織名這類沒有固定格式的實體 |
| 傳統 ML（CRF / HMM + 人工特徵） | 人工設計特徵（前後字、詞性、是否在姓氏表中），模型學特徵到標籤的映射 | 有一定規律但規則寫不完的欄位 | 需要語意理解的情境；特徵設計本身就是瓶頸 |
| 深度學習 NER（fine-tuned BERT） | 預訓練模型已具備語意表示，再以標註語料微調成逐字分類器 | 人名、地址、組織名等模糊實體，能靠上下文判斷 | 沒有檢核碼的概念，號碼類反而可能不如 regex 可靠 |

三者不是取代關係，而是各有守備範圍。實務上最常見的是**規則負責結構化欄位、模型負責模糊實體**，兩路獨立跑完後取聯集。

### 純規則能走多遠：一個真實案例

`dean9703111/data-deidentification` 是一個純前端的去識別化工具，`package.json` 裡只有四個相依套件（`pdf-lib`、`pdfjs-dist`、`jszip`、`@pdf-lib/fontkit`），**沒有任何機器學習套件**。它的技術調研文件明確否決了 NER，理由是需要大型模型下載、且仍需人工覆核。

那沒有模型要怎麼抓中文姓名？它的答案是四層規則防線：

| 層 | 做法 | 規模 |
| --- | --- | --- |
| 姓氏表 | 先確認第一個字是不是姓氏 | 122 個單姓、14 個複姓 |
| 雙分支 regex | 分別處理「姓 + 一字名」與「姓 + 二字名」 | 兩條規則 |
| 停用詞集合 | 把誤判的常見詞整批排除 | 216 個詞條 |
| 前文檢查 | 看命中位置前三個字決定是否採納，擋掉「甲方」「乙方」「任何」「如何」這類 | 約 43 個上下文詞 |

整個專案 3241 行 TypeScript、226 個測試案例。這是「不用深度學習能做到什麼程度」的實證：**結構化欄位幾乎全中，人名靠層層過濾勉強可用，地址與組織名基本放棄。**

下一節的資料流圖記錄了它與模型路線在管線上的差別——骨架相同，差別只在偵測那一段。

### 為什麼「純前端」不等於「在瀏覽器跑 NER」

原本我以為純前端工具之所以可行，是因為 transformers.js、ONNX Runtime Web 這些技術讓輕量 NER 模型能在瀏覽器跑推論。調研之後發現因果關係反過來了。

純前端的動機確實是信任與合規。處理個資若要上傳伺服器運算，等於違背去識別化的初衷，也直接踩到個資法的紅線。

但為了守住「資料完全不離開瀏覽器」這條線，這個專案付出的代價不是「用比較小的模型」，而是**完全不用模型**——因為模型檔案動輒數十 MB，首次載入的體驗與維護成本都不划算。

反過來看公司內部的繁中 NER 服務，選的是後端 Python 加上中研院 CKIP 的 fine-tuned BERT，純 CPU 推論。同一個問題，因為部署形態不同，選型結論完全相反。

所以真正的因果是：**部署形態決定了能不能用模型，而不是模型能力決定了部署形態。**

### 部署形態的第二個後果：授權義務

上面那個結論還有第二面。部署形態不只決定能不能用模型，也決定你背不背開源義務——而這件事必須在寫下第一行程式碼之前想清楚，因為它一旦混進已經上線的服務就很難拆。

去識別化會用到的兩個關鍵套件，授權剛好落在同一條分界線的兩側：

| 套件 | 用途 | 授權 | 網路條款 |
| --- | --- | --- | --- |
| `ckip-transformers` | 繁中 NER | GPL-3.0 | 無 |
| PyMuPDF | PDF 真遮蔽 | AGPL-3.0 | 有（第 13 條） |

GPL 的義務在「散布」時才觸發，而**把程式跑成內部網路服務並不算散布**。所以一個只用到 GPL 元件的內部服務，不產生任何開源義務。

AGPL 第 13 條正是為了補這個缺口而存在：只要使用者透過網路與程式互動，就必須向他們提供原始碼。

於是同一份程式碼，換個跑法就換一套義務：

| 部署形態 | 含 AGPL 元件 | 觸發第 13 條 |
| --- | --- | --- |
| 本機 CLI | 是 | 否 |
| 本機 Web UI（綁 127.0.0.1） | 是 | 否 |
| 內網服務 | 是 | 是 |

所以真正需要隔開的，不是「NER」與「PDF 處理」這兩個功能，而是「AGPL 元件」與「網路服務」這兩個屬性。想通這一層，架構的界線就會自己浮現——反過來也成立：只要沒有別人透過網路連進來，本機 Web UI 一樣安全。

這一節記的是技術面的判斷依據，實際採用前仍應經法務確認。

### 架構與資料流

不論用哪條偵測路線，去識別化管線的骨架是一樣的，關鍵在「壓平再分派」這個模式：把有結構的文件（PDF 的頁與文字區塊、Word 的 XML 節點）壓成一條連續字串，所有偵測與替換都在扁平的字元位置上運算，最後再把結果分派回原本的結構。

這個模式之所以必要，是因為個資很容易跨越結構邊界——PDF 為了調整字距，可能把「王小明」拆成兩個文字區塊；地址則常常跨行。若直接在結構節點上比對，這些都會漏抓。

### 讀原始碼才確認的一件事：offset 的語意

實作前有個疑慮：服務端允許的文字長度上限是 5000 字，而 BERT 的序列上限是 512 個 token。超出的部分會怎麼樣？如果是被截斷，那就是**個資靜默漏抓**——最危險的那種失敗，因為它不會報錯。

去讀 `ckip-transformers` 的原始碼後，答案是不會。長度超標時它另起一段，而不是丟棄：

```python
if len(input_ids_sent) + word_length > max_length:
    input_ids.append(input_ids_sent)
    input_ids_sent = []
```

更關鍵的是回傳的位置。它給的 `idx` 是 `index_char`——**原始輸入字串的字元位置**，不是內部切段後的相對位置。

這一點決定了整條管線能不能成立。模型回傳的位置可以直接餵進「壓平再分派」的對照表；若 offset 是相對於內部切段的，就得自己還原位移。而那正是最容易出錯、又最不容易被發現的一類 bug——**貼錯位置的假名，看起來跟貼對的一樣正常。**

殘留的風險小得多但仍存在：連續超過 510 個 token 都沒有出現分隔符的文字，會在任意位置被硬切，跨越切點的實體會解碼失敗。契約文件的表格與清單有機會踩到。

這件事留下的教訓是：**要依賴一個函式庫的 offset 語意，就去讀它的原始碼，不要讀 README。** 並且要為這個語意寫一條測試（斷言 `text[start:end]` 等於回傳的實體字串），這樣升級版本時語意若改變，會立刻炸出來，而不是讓下游默默貼錯。

### 把模型接成服務之後才浮現的成本

選擇用現成模型，省掉的是訓練與標註成本；但成本並沒有消失，而是搬到了「服務化」這一端。這四項都是讀完服務程式碼後才看見的：

| 成本 | 成因 | 徵狀 |
| --- | --- | --- |
| 超額訂閱 | Web 框架的執行緒池與 PyTorch 的核心層平行化相乘 | 並發數越高，每個請求反而越慢 |
| 冷啟動 | 模型是懶載入，第一個請求才觸發載入 | 服務已回報健康，但模型還沒就緒 |
| padding 浪費 | 批次推論會把所有片段補齊到最長那一筆的長度 | 批次內長度落差越大，浪費的計算越多 |
| 逐筆呼叫 | 介面一次只吃一個字串 | 處理 N 頁就是 N 次模型呼叫，放棄了批次的效益 |

第一項最違反直覺，所以值得單獨拆開看。兩層平行化各自都合理——框架用執行緒池讓同步端點不阻塞事件迴圈，PyTorch 用多執行緒吃滿 CPU——但它們相乘之後，執行緒數會遠超過核心數，變成互相搶佔。

判斷法則其實很單純：**CPU 密集的工作，並發度應該逼近核心數，而不是逼近請求數。**

### 真遮蔽與假遮蔽

比模型準確率更關鍵的一件事：**把文字蓋住不等於把文字刪掉。**

在 PDF 上畫一個黑色或白色矩形，視覺上個資消失了，但原始文字仍然存在於 PDF 的內容串流裡。用滑鼠選取複製、或用任何文字抽取工具打開，個資就會原樣跑出來。這是經典的「假遮蔽」事故，也是新聞上讀到的「政府公文塗黑後仍被還原」的成因。

要真的刪掉，必須從內容串流中移除對應的文字繪製指令，而不是在上面疊圖層。這也直接決定了驗收方式：

> 對每一份輸出檔重新抽取文字，斷言所有被偵測到的原始字串一個都找不到。

這條測試通過之前，模型準確率再高都沒有意義。

### 期末專案方向

綜合以上，期末專案不走「自己訓練一個 NER 模型」，而是走**評估與後處理改善**，並額外拉一條純規則的對照線：

| 項目 | 內容 |
| --- | --- |
| 受測對象 A | 現成的 CKIP fine-tuned BERT，原樣不動 |
| 受測對象 B | 純規則路線（姓氏表、雙分支 regex、停用詞、前文檢查），作為對照組 |
| 測試集 | 自行標註 200 至 300 句真實文件語句 |
| 指標 | 各類別的 entity-level precision、recall、F1 |
| 產出 | 兩條路線的逐類別對照表、漏抓型態分析、後處理規則層與其改善幅度 |

選這條路的理由是：真正的瓶頸不是模型架構而是**標註資料**。微調需要數千句標註（估計 30 至 60 小時的純標註工），而資料是真實個資、不能外包標註；評估只需要兩三百句，一兩天可完成，卻能產出目前沒有人量測過的資訊——CKIP 是在新聞語料上訓練的，它在契約文件上表現如何，並沒有現成答案。

要加上對照組 B，則是因為單獨一個 F1 數字讀不出意義，得有比較對象才知道那個數字算好還是壞。而且這一步正好把前面那張選型光譜表從紙上調研變成實測——「純規則抓得到什麼、抓不到什麼」目前只是引述來的結論，跑過同一份測試集之後就會變成自己的數據。

預期的弱點在地址與組織名，這也正好是純規則路線同樣放棄的那一塊。兩條路線在同一處失守，這件事本身就是結果的一部分。

關於量測順序有一點要分清楚：服務端的超額訂閱只影響延遲，不影響準確率——執行緒互相搶佔不會改變模型的輸出。所以準確率那條線現在就能開始量，不必等服務調校；只有延遲基線必須先把執行緒環境弄乾淨再量，否則量到的是搶佔而不是模型本身的能力。

### 需要補的先備知識

這條路線真正執行的深度學習動作只有一個：推論。但要能解釋「為什麼會漏抓」，需要懂的東西遠多於「跑一次推論」，而且集中在課程沒有涵蓋的那一塊。

| 技術 | 會不會實際動手寫 | 需不需要懂 | 理由 |
| --- | --- | --- | --- |
| 推論（forward pass） | 只是呼叫 API | 淺 | 一個 POST 就結束了 |
| 序列標註與 BIO 標籤體系 | 會，標註測試集時 | 深 | 這是 NER 的問題形式化，決定 ground truth 長什麼樣 |
| 中文 char-level tokenization | 不會 | 深 | offset 語意與 510 token 硬切風險都源自這裡 |
| 預訓練加微調的範式 | 不會 | 深 | 新聞語料訓練、契約文件推論的落差就是整個專案的論點 |
| Transformer 自注意力 | 不會 | 中 | 只需要到「為什麼上下文能判斷人名」，不必推導 QKV |
| 訓練迴圈與反向傳播 | 不會 | 已具備 | 第 10、11 週手刻過一次 |
| RNN、LSTM 加 CRF | 不會 | 選配 | ch15 可整章跳過，除非要再多加一條對照線 |
| CNN、GAN、GNN、強化學習 | 不會 | 不需要 | ch14、17、18、19 與本專案無關 |

課程教到的極限是第 10、11 週：手刻過前向與反向傳播、知道 tensor 與 autograd 怎麼記帳。序列標註、預訓練加微調的範式、Transformer 都沒教，要自學 ch16 的 BERT 與 token classification 那半章。

要補的東西按「會不會擋住進度」排成四層：

| 層級 | 內容 | 課程有沒有教 | 何時能開始 |
| --- | --- | --- | --- |
| Tier 0 | 標註規範設計 | 無關 | 現在，不必等任何進度 |
| Tier 1 | 序列標註的評估方法論 | 只教了分類版本 | 與標註同時進行 |
| Tier 2 | 模型內部與訓練分佈落差 | 沒教 | 分析結果之前 |
| Tier 3 | 量測環境的工程議題 | 沒教 | 只有延遲那條線需要 |

Tier 0 是整個專案最被低估、也最可能毀掉數字的一環。「臺北市信義區松智路 1 號 5 樓之 3」算一個地址實體還是拆成多個？「王小明先生」的敬稱在不在邊界內？「甲方（○○股份有限公司）」的括號算不算組織名的一部分？這些沒有標準答案，但規範必須盡量對齊 CKIP 訓練時採用的規範，否則量到的「錯誤」有一部分只是規範不合，不是模型能力問題。這也是評估類專案最容易被質疑的地方。

Tier 1 是專案的主體，而它跟第 7 週學的分類評估並不是同一套：

| 概念 | 課程涵蓋 | 為什麼這裡不一樣 |
| --- | --- | --- |
| entity-level 對 token-level 計分 | 沒教 | 抓到「王小」漏掉「明」，token-level 得 0.67 分，entity-level 是 0 分。去識別化只有後者有意義，漏一個字就是外洩 |
| 嚴格匹配對部分匹配 | 沒教 | seqeval 的預設模式與 strict 模式結果不同，報告要講清楚報的是哪一種 |
| micro 對 macro 平均 | 部分 | 組織名樣本少、人名樣本多，micro 會被人名淹沒，看不出預期中的弱點 |
| 樣本數與信賴區間 | 沒教 | 200 至 300 句這個規模的最大風險 |

最後一項是目前規劃裡最脆弱的地方。若組織名在整份測試集只出現二十來次，那個 F1 的誤差範圍會寬到結論站不住。因應方式是標註前先抽三十句數一數各類別的出現頻率，往回推兩三百句能得到多少實體；撐不到一定數量的類別，要麼加大樣本，要麼在報告裡誠實標成樣本不足。

Tier 2 不需要會寫 BERT，只需要能回答「為什麼會漏」。三個成因分別是訓練語料的分佈落差（新聞裡的地址是「台北市」，契約裡是完整門牌與樓層，後者在訓練分佈中幾乎不存在）、模型沒有檢核碼的概念（`A123456789` 與 `A123456788` 在它眼裡沒有差別，這解釋了號碼類為什麼 regex 反而贏）、以及超長無分隔符文字被硬切造成的標籤斷裂。
